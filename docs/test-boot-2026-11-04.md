# Test boot: Jet Set Radio (Dreamcast) on dream-recomp

2026-11-04, cloud sandbox (Linux x64, 4 cores, clang 18.1.3). Experiment only: nothing was committed
or pushed anywhere. The disc and everything made from it (extracted files, generated C++, binaries,
screenshots) stay in the sandbox. This file holds only metadata: hashes, addresses and counts.

## Result in one paragraph

The **translated** build, the one a port would ship, now **boots Jet Grind Radio to its title
screen and stays up**. With no input it shows the title screen at 46 s and moves on to the attract
demo. With scripted presses it goes through the main menu into a stage and is still on that
stage's TIME OVER screen at 5 and at 10 minutes. On the final config, both 600 guest-second runs
(35,977 frames each) had **0 faults, 0 traps, 0 unmapped accesses and 0 calls falling back to the
interpreter**, at 1.7x and 1.9x real time headless. The frame-82 stop from the first
test boot was a bug in dream-recomp's translator, not in the game or the config: when a translated
function was resumed partway through, its interrupt check recorded the function's first
instruction as the place to return to, so a task switch inside that interrupt later ran the
function's prologue a second time. The fix is two lines in the emitter plus a unit test (patch
02). Three config seeds then removed the last interpreter fallbacks. Still open for a port:
modifier volumes aren't drawn (JSR uses them in every 3D frame), nobody has played a stage yet,
and each config change costs a 15-minute rebuild.

## The frame-82 fault, found and fixed

**How it was found.** Interpreting the 285 functions in 0x0C0B0000 to 0x0C0B8000 cleared the fault,
but neither half did. Narrowing by address range (`DREAM_INTERP_FUNCS`) found that what mattered
was 0x0C0B2C04, a call-return point inside fn_0c0b2a60, not a whole function. A write log of the
translated run against a mixed run then gave the first real divergence: guest write #13,434,719, in
frame 69. The interrupt handler at VBR+0x640 saved SPC = 0x0C014070 (fn_0c014070's first
instruction) where the mixed run saved 0x0C0140A4 (the point that body had been resumed at). 6,949
writes later the translated build ran fn_0c014070's prologue again, and from there the two runs
drifted apart until the call through 0xFFFFFFFF at frame 82.

**Cause.** JSR runs its game logic as tasks that switch away partway through a function: 4,302
non-local returns and 9,917 resumes in the first 2 guest seconds. dream-recomp supports this by
giving every translated function a resume entry (`fn_X__resume(c, m, resume_pc)`) that jumps to
the block it was left at. That entry polls for interrupts first, and the poll set `c.pc` to the
function's entry even when `resume_pc` named a later block. The handler saves `c.pc` as SPC, so
when the interrupt switched tasks, the task later returned to the function's first instruction.

**Fix.** The entry poll now records `resume_pc ? resume_pc : entry`
(`translator/src/emit/emit.cpp`). `translator/tests/test_resume_poll.cpp` emits a two-function
image and checks the poll's text and the resume label. It fails without the fix and passes with
it. Generated code was not edited by hand. This is a general emitter bug: any title whose
interrupt handler switches tasks would hit it, so it's worth offering upstream once you say so.

## The seeds: 0x0C02F5A4, then 0x0C031AA8 and 0x0C039AF0

After the fix, a 180 s translated run (r7) still made 13 calls to 4 addresses the translator hadn't
found, and ran them interpreted. 0x0C02F5A4 is a whole function (its prologue follows a literal
pool) reached only through a function table read at 0x0C030546 and called at 0x0C03054C. The other
three were mid-function addresses (0x0C02F796, 0x0C02F7BA inside it, and 0x0C01BD94, a call-return
address), which the runtime resolves itself, so only 0x0C02F5A4 went into `[functions] extra`.

| Measure | Before seed | After seed |
|---|---|---|
| Functions | 12,848 | 12,427 |
| Instructions | 718,331 | 714,141 |
| Bytes decoded | 1,216,132 of 1,446,550 | 1,216,374 of 1,446,830 |
| Switch tables | 121 | 117 |
| Untranslated calls with presses | 13 in 180 s (r7) | 0 in 600 s (r8) |
| Rebuild | | 14 min 25 s |

All 422 removed entries lie inside a function that is still there: 326 were pointer-pass guesses,
95 branch-derived fragments and 1 a sweep guess now inside the seeded function. Nine existing
functions got longer. The likely mechanism, read from `discover.cpp` but not traced: discovery
walks seeds and call targets before its pointer pass, and the pointer pass skips addresses already
decoded as code. With the seed, 12 functions are reached earlier, so look-alike pointers into them
no longer become separate overlapping functions.

The regression gate (40 s attract and 40 s gameplay scenarios) reports CHANGED write hashes for
both. The only counter that differs is untranslated call targets, 3 to 0 in each scenario; frames
(2,408), the final pc and every other counter match. Interpreted calls cost different cycles from
translated ones, which moves where interrupts land and so the order of writes. I judge the change
harmless.

**Two more holes, from the no-input run.** r9 left the game on its title and attract demo, which
the press script skips, and made 34 interpreted calls to 7 addresses. Two are holes of the same
kind as 0x0C02F5A4, called through the same dispatcher at 0x0C03054C: 0x0C039AF0 (6 calls) and
0x0C031AA8 (2), each a register-saving prologue right after a literal pool, listed in a pointer
table at 0x0C175B90 and 0x0C175B94. The other five (0x0C031C96, 0x0C039CCE, 0x0C039CEE,
0x0C039CF4, 0x0C039CFA) are addresses inside the sweep-found functions that follow them, so they
aren't seeded. The interpreter runs these correctly (no faults), but a build without it couldn't.
Seeding both (rebuild 14 min 21 s) took discovery to 12,259 functions, 712,697 instructions, 120
switch tables and 1,216,786 of 1,447,388 bytes decoded. Against the stub build, all 592 entries
that are gone lie inside a function that remains (433 pointer, 156 branch, 3 sweep: the 3 sweep
functions are now the tails of the 3 seeds). The gate, against the one-seed build: **attract
identical, gameplay identical** (those 40 s scenarios never reach the new functions). r10 and r11
below are this build.

## What a port would still need

1. **Playing a stage.** The presses reach a stage, but nothing steers in it, so its timer runs out.
   Next is a press script that moves and grinds, and then the gate's gameplay scenario pointed at
   it.
2. **Modifier volumes.** `docs/runtime-render.md`: "decoded but not drawn". JSR uses them in every
   3D frame (r8's last frame: 39 opaque and 1 translucent). It needs a stencil pass in the Vulkan
   renderer, and JSR would be its first test.
3. **Iteration cost.** Every config change re-emits 81 MB of C++ and recompiles for about 15
   minutes. Splitting the generated unit would shorten the loop.
4. **Upstream.** Patches 01 and 02 fix dream-recomp itself. Sending them to phobos665/dream-recomp
   is your call; nothing has been sent.
5. Our rules' gaps from the first report still stand: no OpenGL renderer, and no SteamOS testing.
